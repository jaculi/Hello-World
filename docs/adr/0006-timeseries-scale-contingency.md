# ADR-0006：时序库规模预案——TimescaleDB 基线与专用时序库触发阈值

- 状态：**Accepted**
- 日期：2026-09-05
- 关联：[ADR-0003](./0003-technology-stack-baseline.md)、[BP-03 §6](../blueprint/03-data-architecture.md)、[BP-04 §3.2/§9](../blueprint/04-technology-architecture.md)

## 背景（Context）

BP-03 §6 定了时序治理机制（TTL/降采样/冷热分层/质量评分/租户分桶），BP-04 §3.2 选 TimescaleDB 为首选（与 PostgreSQL 同栈）。本 ADR 把"规模触顶再引入专用时序库"从模糊表述落为**可测量的触发阈值与迁移路径**，避免过早引入第二套数据栈、也避免规模失控后被动迁移。

## 决策（Decision）

### 1. 基线：TimescaleDB（保持不变）

- hypertable 分桶：按 `tenant_id + 站点 + 时间` 二级分桶（BP-03 §11 开放问题 1 就此闭环：租户内再按站点分桶，T1/T2 租户独立实例/库天然物理分桶）；
- TTL、连续聚合（1m/1h/1d）、列压缩启用原生能力（对应 BP-03 §6 降采样与冷热分层）；
- K8s 运行采用云中立 PostgreSQL Operator（如 CloudNativePG 类），跨 AZ 流复制 + PITR（BP-07 §4.4）。

### 2. 专用时序库触发阈值（满足任一即启动评估，两项即启动迁移）

| 维度 | 阈值（单 Cell） |
|---|---|
| 写入吞吐 | 持续 > 50 万行/s（压缩前） |
| 存储规模 | 原始数据 > 50 TB 或月增 > 10 TB |
| 查询 SLO | 压缩后聚合查询 P95 连续两周超 BP-07 SLO 预算的 2 倍，且经索引/聚合优化无效 |

阈值校准依赖 BP-07 容量三指标（连接数/消息速率/AI 峰值）的首个行业压测数据——本 ADR 属"预案"，压测后修订阈值参数（不需新 ADR，属参数修订）。

### 3. 迁移路径（触发后执行，接口不变）

1. **候选评估**：TDengine / InfluxDB（物联网场景优先级）——按租户分桶能力、K8s 自托管、压缩比、聚合查询性能打分；
2. **影子双写**：BC-I3 写入管道并行写新库（只写新数据，不回填）；
3. **历史回灌**：冷数据本就以 Parquet 存对象存储（BP-03 §6），按租户/站点批量回灌新库；
4. **读切换**：查询只经 BC-I3 API 收口（BP-02 §3.2），切换对上层透明；按租户灰度切流；
5. **旧库退役**：确认一致后下线，迁移全程审计留痕。

### 4. 架构保障（现在就做对）

- 所有遥测读写必须经 BC-I3/I2 API，禁止其他 BC 直连时序库（BP-02 硬约束）——这是迁移路径成立的唯一前提。

## 重审触发条件

阈值首次接近（达到 70%）时向架构评审会预警（BP-07 §5 季度节奏），评估是否提前启动。

## 后果（Consequences）

**正面**：单一数据栈维持到规模化之前，运维面小；迁移有据可依、接口透明、冷数据可重建（BP-03 §7）。
**负面/约束**：TimescaleDB 在极端写入下的上限依赖压缩与硬件，需压测数据校准；迁移期双写有约 1 个季度的资源冗余成本。
