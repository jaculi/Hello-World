# ADR-0001：平台定位与核心架构原则

- 状态：**Accepted**
- 日期：2026-09-05

## 背景（Context）

JSL 需要服务企业运营、工业 IoT、智慧楼宇、智能农业、智能医疗、远程警备等差异显著的行业，并支持未来行业扩展。各行业对设备接入、业务流程、智能化与安全的要求不同，但又共享大量基础能力（租户管理、设备管理、身份权限、AI 算法、运营运维）。

需要明确：平台以何种形态交付、AI 在架构中处于什么位置、平台与生态的边界在哪里，以避免：

- 按行业烟囱式重复建设；
- AI 被做成孤立业务系统，无法被各域复用；
- 平台内核随行业定制不断腐化，难以长期运营。

## 决策（Decision）

### 1. 平台定位

JSL 定位为**多租户 AIoT 智能运营平台**，以 SaaS 形态交付，面向长期企业运营。

### 2. AI 横向化，不做独立 AI 业务线

AI 作为**横向智能能力层**存在，以标准服务形式被 Business 域、IoT 域、安全运营域及各行业模块调用；不建设独立的"AI 业务平台"。AI 模型/算法以插件方式注册接入能力层。

### 3. 稳定内核 + 可插拔行业

平台内核 = 多租户基座 + IoT 接入 + AI 能力层 + 安全运营 + 开放 API 网关 + 插件运行框架，保持长期稳定；行业差异通过**行业模块插件**装配，新行业接入不动内核。

### 4. 开放生态

- **开放 API（北向）**：平台能力经 API 网关对外开放，配套认证授权（OAuth2 / API Key）、限流、计费、版本管理、开发者文档与沙箱。
- **插件 SPI（南向/扩展点）**：设备协议插件、AI 能力插件、行业模块插件、业务功能插件四类插件通过标准 SPI 接入。
- 插件受租户隔离、统一 IAM/RBAC、安全沙箱、资源配额与生命周期管理（注册/审核/上架/启停/升级）约束。
- 预留开发者门户与应用/插件市场方向。

### 5. 工程基线（八项，长期约束）

1. 多租户 SaaS；
2. 国际化 i18n（语言/时区/币种，Day-1 内建）；
3. Business + IoT + AI 融合；
4. 企业级 Blueprint 文档体系（蓝图驱动开发）；
5. ADR 架构决策记录；
6. DDD 模块化设计（限界上下文划模块，模块间仅经契约交互）；
7. 统一 IAM / RBAC（覆盖人、插件、API、数据权限）；
8. 长期企业运营目标（可运维、可计量、可演进、成本可控）。

### 6. 分层结构

```
生态层（开发者门户 / 插件市场 / 第三方应用）
开放 API 网关（认证/鉴权/限流/计费/版本）
行业模块层（企业运营 / 工业IoT / 楼宇 / 农业 / 医疗 / 警备 / ...）
Business 业务域 │ IoT 设备域 │ 安全运营域
AI 横向能力层（模型/算法插件化 + 策略闸门）
插件运行框架（沙箱 / 生命周期 / 租户权限 / 配额）
多租户平台基座（隔离 / 数据 / 权限 / 计量 / i18n）
```

## 后果（Consequences）

### 正面

- 新行业以插件/模块方式接入，边际成本低，内核可持续复用；
- AI 能力一次建设、全域复用，避免重复造模型与重复采购；
- 开放 API 与插件机制形成生态飞轮，第三方可在不改内核的前提下扩展平台；
- 八项基线使 i18n、租户隔离、权限、审计、计量等横切能力无技术债地内建。

### 负面 / 约束

- 内核 API 与插件 SPI 一旦发布即承担兼容性责任，演进需版本化管理；
- 插件沙箱、多租户隔离、权限穿透校验增加平台初期复杂度；
- AI 能力层需同时满足多行业调用的通用性与性能/隔离要求，对能力抽象要求高；
- 所有模块必须遵守 DDD 边界与 Blueprint/ADR 流程，团队纪律要求高。

### 后续决策依赖

- AI 能力层的调用治理由 [ADR-0002](./0002-ai-governance-and-five-factor-gate.md) 规定；
- 插件 manifest/SPI 细节、API 网关与认证方案、租户隔离模型待后续 ADR 细化。
