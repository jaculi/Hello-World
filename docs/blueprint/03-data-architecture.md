## 1. 目的与范围

本文定义 JSL 平台的数据架构：

1. **数据分类与存储形态映射**：每类数据放什么存储、什么形态；
2. **租户数据隔离模型**：隔离策略分层与选择规则；
3. **数据模型全局约定**：归属链、审计字段、i18n 数据、主数据管理；
4. **领域事件与 Schema 管理**：事件信封、注册表、版本兼容；
5. **时序数据治理**：保留、降采样、冷热分层；
6. **AI-Ready 数据标准**：数据质量评分体系（五因子之"数据质量"的裁决依据）、特征/标注/数据集规范。

硬约束：

- **租户数据物理或逻辑严格隔离，任何查询必须收敛到租户范围**（纵深防御，仅靠应用层过滤不够）；
- **跨上下文禁止直连库表**（BP-02 §1），数据只经 API/事件/物化视图流动；
- 每类有价值的数据**接入即登记元数据与质量评分**（AI-Ready by Default，ADR-0002）；
- 医疗/警备等受监管行业数据须支持**合规留存与可追溯**（细节在 BP-05）。

## 2. 数据分类与存储形态映射

### 2.1 数据分类

| 类别 | 内容 | 生产者（BC） | 特征 |
|---|---|---|---|
| D1 时序遥测 | 设备上报的测点数据 | I3 | 写多读少、体量最大、时间索引 |
| D2 事件流 | 领域事件、审计、AI 裁决 | 全部 BC / P5 / A2 | 只追加、回放与追溯 |
| D3 主数据 | 租户/组织/站点/资产/人员/产品/设备档案 | P1、B1、I2 | 变更低频、强一致、被广泛引用 |
| D4 业务过程 | 工单、警情、流程实例、巡更记录 | B2、S2、S3 | 状态机、需流程历史 |
| D5 分析数据 | 物化视图、指标、报表快照 | B3 | 读优化、可重建 |
| D6 媒体对象 | 录像、图片、抓拍、文件 | S1、A1 | 大对象、生命周期管理 |
| D7 AI 资产 | 特征集、数据集、标注、模型版本元数据 | A1、A3 | 血缘要求高 |
| D8 平台配置 | 策略、规则、插件 manifest、i18n 词条 | P2、E1、A2 等 | 版本化、变更需审计 |

### 2.2 存储形态总图

```
┌────────────────────────────────────────────────────────────────┐
│ 关系库（强一致/事务）：D3 主数据、D4 业务过程、D8 配置             │

├────────────────────────────────────────────────────────────────┤

├────────────────────────────────────────────────────────────────┤
│ 事件日志/流存储：D2（事件总线 + 持久日志，回放窗口 ≥30d）          │
├────────────────────────────────────────────────────────────────┤
│ 对象存储：D6 媒体（桶按租户前缀隔离 + 生命周期规则）               │
├────────────────────────────────────────────────────────────────┤
│ 搜索引擎：主数据/工单/警情检索、跨域全文（读侧，经事件同步）        │
├────────────────────────────────────────────────────────────────┤
│ 缓存：会话、设备影子热点、字典（租户键前缀隔离）                   │
```

具体产品选型（如 PostgreSQL、TimescaleDB/InfluxDB、Kafka、MinIO/S3、ES、Redis）由 BP-04 的 ADR 决定，本文只定形态与约束。

## 3. 租户数据隔离模型

### 3.1 隔离策略分级

| 级别 | 模式 | 适用 | 防护 |
|---|---|---|---|
| T1 | **独立库**（每租户一库，甚至独立实例） | 独立部署/专有云大客户、监管要求物理隔离行业（医疗专有云） | 物理隔离 |
| T2 | **独立 Schema**（共享实例，每租户一 schema） | 中大型租户、数据敏感度高的行业租户 | 逻辑强隔离 |
| T3 | **行级隔离**（共享表 + `tenant_id` 强制过滤 + 行级安全策略 RLS） | 标准小微型租户、平台级配置类数据 | 应用 + 数据库双层强制 |

选择规则：

- 默认 T3（SaaS 规模化成本）；租户开通时按**套餐与合规要求**选择升级到 T2/T1；
- 隔离级别是**租户级元数据**（BC-P1 登记），数据访问层据此路由；
- 同一租户的所有数据（关系/时序/对象/缓存）保持一致级别（时序与对象用"租户前缀桶/表"等价实现）。

### 3.2 强制收敛机制（纵深防御）

1. **应用层**：所有 BC 数据访问必须携带租户上下文（BP-02 §2 的 `tenant_id/org_id/site_id`），ORM/DAO 层自动注入过滤条件，禁止裸 SQL 绕过；
2. **数据库层**：T3 启用行级安全策略（RLS，以会话变量绑定租户）；T2 独立 schema 权限隔离；
3. **网关层**：开放 API 与插件调用强制重写/校验租户范围，插件**永远拿不到跨租户句柄**；
4. **异步路径**：事件信封携带 `tenant_id`，消费者按租户路由到对应隔离单元（T1/T2 场景按租户分区分发）；
5. **交叉校验**：定期对账任务抽样检测越界引用（如资产归属 tenant ≠ 请求租户即告警，入 P5 审计）。

## 4. 数据模型全局约定

### 4.1 归属链与公共字段

所有租户域数据必须满足归属链：

```
tenant_id → org_id（可空）→ site_id（可空）→ 业务对象
```

公共字段（所有表强制）：

| 字段 | 说明 |
|---|---|
| `tenant_id`（必填） | 租户；平台级配置表除外 |
| `created_at / created_by / updated_at / updated_by` | 审计四件套 |
| `version` | 乐观锁 |
| `is_deleted / deleted_at` | 软删除（审计与恢复要求） |
| `row_id`（全局主键） | UUID/ULID，跨库合并与事件引用安全 |

### 4.2 i18n 数据策略

- 业务数据多语言采用**消息码 + 翻译表**模式：主表存 `i18n_key`，翻译表 `(key, locale, text)`；运行时按用户 locale 渲染；
- 领域事件与 API 报文只携带**消息码 + 参数**（BP-02 §1），禁止携带已渲染文本入库；
- 时区：统一存 UTC，展示层按租户/用户时区转换；货币：存币种 + 原值，换算在展示/计费层。

### 4.3 主数据管理（MDM，BC-B1）

- **Golden Record**：Space / Asset / Person / Product 以 BC-B1 为唯一权威源；其他域只存 `row_id` 引用（配合本地冗余"展示快照"，经事件刷新）；
- **站点子类型扩展**：行业模块经 MasterData SPI 声明子类型（如 `Building`、`Greenhouse`、`Ward`），实现为：主表 + 行业扩展表（`site_ext_<module>`），扩展表归属行业插件命名空间，**不修改内核主表结构**；删除插件时扩展表级联停用（数据留存策略按套餐）；
- 引用完整性：跨域引用经事件对账（BP-02 §5.2），不做跨库外键。

## 5. 领域事件与 Schema 管理

### 5.1 事件信封（Event Envelope，统一契约）

```json
{
  "event_id": "ULID",
  "event_type": "iot.telemetry.quality-scored",   // 域.聚合.动作
  "event_version": "1",
  "tenant_id": "...", "org_id": "...", "site_id": "...",
  "occurred_at": "RFC3339 (UTC)",
  "producer": "bc-i3",
  "trace_id": "...",
  "payload": { "...": "领域负载；文本一律消息码+参数" }
}
```

### 5.2 Schema 注册表与兼容策略

- 所有事件与开放 API 的 Schema 登记**注册表**（BP-06 归口实现），发布前校验；
- 兼容规则：同一 `event_type` 的次版本升级必须**向后兼容**（只增字段、不改语义、不删必填）；破坏性变更 = 新事件类型 + 双写过渡期；
- 消费方幂等（按 `event_id` 去重），乱序容忍（按聚合 ID 分区）。

## 6. 时序数据治理（D1）

| 机制 | 规则 |
|---|---|
| 保留策略（TTL） | 按套餐分级：原始数据默认 90d（可配），聚合后数据 1–2 年 |
| 降采样 | 写入即异步生成 1m/1h/1d 聚合（avg/min/max/count），告警与报表读聚合 |
| 冷热分层 | 热（SSD，在线查询）→ 温（压缩列存）→ 冷（对象存储 Parquet，可回灌） |
| 数据质量评分 | 写入管道同步评估（见 §8），评分随测点元数据存储，供 AI 闸门读取 |
| 租户隔离 | 时序库按租户建桶/超级表（T2/T1 物理分桶），查询强制租户路由 |

## 7. 分析与读侧（D5）

- BC-B3 只消费**事件**构建物化视图（各域读模型），不直连其他 BC 的库（BP-02 §3.3）；
- 跨域驾驶舱 = 物化视图 + 聚合指标（按租户/站点/时间预聚合）；
- 分析数据**可随时重建**（事件日志是事实源），因此不承担强一致责任。

## 8. AI-Ready 数据标准（承接 ADR-0002）

### 8.1 数据登记与质量评分（五因子之"数据质量"的数据源）

每类数据接入时在元数据中心登记（BC-A3 归口，BP-02 §3.5）：

| 质量维度 | 度量 | 权重建议 |
|---|---|---|
| 完整性 | 期望测点/字段的非空率、断链时长 | 高 |
| 准确性 | 越限率、跳变/冻结检测、校准偏差 | 高 |
| 时效性 | 上报延迟 P95、停报率 | 高 |
| 一致性 | 单位/枚举/主引用一致性（对 MDM） | 中 |
| 样本充分性 | 历史样本量、正负样本比例（监督场景） | 中 |

输出：**数据质量分（0–100）+ 分维度明细**，写入元数据中心；BC-A2 闸门实时读取，作为"数据质量因子"的量化依据（阈值按场景在 AI Policy 中配置）。

### 8.2 特征 / 标注 / 数据集规范（D7）

- **特征表**：统一命名 `<domain>_<object>__<feature>`，注册特征血缘（来源测点/加工逻辑/版本）；
- **数据集**：版本化快照（时间窗 + 筛选条件 + 特征清单），训练与评估可复现；
- **标注**：标注任务、标注人、一致性抽检（双人标注一致率）；标注结果计入数据集版本；
- **血缘**：`数据源 → 特征 → 数据集版本 → 模型版本` 全链路登记，模型效果退化时可回溯数据因素；
- 隐私数据（人脸、健康体征等）进入 D7 前必须完成**脱敏/匿名化或授权绑定**（规则细化在 BP-05）。

### 8.3 落地检查表（每个 AI 场景上线前的数据侧门禁）

1. 场景所需数据是否已登记元数据与质量评分？
2. 质量分是否达到 AI Policy 配置的阈值？
3. 样本是否充分且覆盖风险场景（含边界/异常样本）？
4. 特征与数据集是否有版本与血缘？
5. 敏感字段是否完成合规处理？

——五项全部通过，闸门的"数据质量因子"才能判定通过；否则降级（如仅 L3 辅助或暂缓启用）。

## 9. 数据流示例（延续 BP-02 §5.3 能耗场景）

```
空调电表遥测（D1）
  → 写入管道：质量评分（§8.1）→ 原始区（TTL 90d）→ 1m/1h 降采样（D5 可用）
  → `iot.telemetry.quality-scored` 事件（信封含 tenant/site）
BC-I4 告警事件 → BC-A2 读取质量分（闸门因子②）
BC-A1 推理 → 特征服务读特征表（D7，血缘已登记）→ `ai.inference.completed` → 用量入 BC-P3
工单流转（D4）→ `biz.ticket.closed` → BC-B3 物化视图（D5）→ 驾驶舱
全链路：P5 审计（D2）留存 ≥ 合规要求
```
